## 1. Стек и куча

**Стек** — память горутины под локальные переменные вызовов: кадры кладутся
и снимаются перемещением указателя стека — аллокация почти бесплатна,
освобождение тоже. У каждой горутины свой стек, стартующий с 2 КБ (8КБ в
новых версиях) и **растущий**: при нехватке места рантайм аллоцирует в
два раза больше и копирует стек (перенос указателей), поэтому «большая
рекурсия» в Go живёт, пока есть память.

**Куча** — общая память, переживает кадр, где создана переменная;
управляется сборщиком мусора. Аллокация дороже стека, а жизнь на куче
включает налог GC: трассировка достижимости, write barriers, паузы.

**Кто решает, где жить переменной — escape analysis компилятора.**
Локальная переменная умирает вместе с кадром → стек. Убегает на кучу,
когда её жизнь переживает функцию:

- возвращается по указателю (`return &x`, `new(T)` с возвратом);
- сохраняется в замыкании/глобальной переменной/канале;
- попадает в interface{} (boxing часто прячет указатель);
- слишком велика или размер неизвестен на компиляции (большой слайс,
  `make([]byte, n)` с переменной n);
- разделяется горутиной, пережившей кадр.

Практика и собес-ловушки:

- передача значения в функцию — копия на стеке (дёшево); передача
  указателя может заставить переменную убежать — «указатель для
  экономии» большого числа мелких вызовов может дать обратный эффект;
- `go build -gcflags="-m"` — посмотреть решения escape analysis;
- строки, слайсы, мапы всегда содержат часть на куче (данные буфера);
- предаллокация (`make` с ёмкостью) не меняет стек/кучу, но уменьшает
  число промежуточных аллокаций и нагрузку GC;
- GC — параллельный tri-color mark & sweep с write barrier'ами; настройка
  GOGC (частота) и GOMEMLIMIT (мягкий потолок памяти) — прицельные
  рычаги, `runtime.ReadMemStats` / pprof allocs — диагностика.

## 2. KISS и DRY

- **KISS** (Keep It Simple, Stupid) — из всех решений, решающих задачу,
  выбирать самое простое: меньше кода, меньше ветвлений, меньше
  зависимостей — меньше мест для бага и дешевле поддержка. Против
  KISS-нарушений: «универсальный» хелпер на 8 параметров, магия
  конфигурации, преждевременная оптимизация.
- **DRY** (Don't Repeat Yourself) — каждое знание (правило, константа,
  логика) должно иметь единственное представление в системе. Дублирование
  кода = дублирование поддержки: правку забыли внести во втором месте —
  баг. Но DRY — про повторение *знания*, а не про внешне похожие
  фрагменты: два одинаковых switch'а в разных слоях могут отражать разные
  причины изменений.

**Баланс на практике** (то, что спрашивают следом):

- KISS первичен: DRY служит поддерживаемости, и когда обобщение ради DRY
  усложняет код — оно вредит. «Дублирование дешевле неправильной
  абстракции» (Sandi Metz): свести два случая в один модуль просто,
  распутать преждевременную абстракцию на три случая — больно.
- Правило трёх: допускаем второе дублирование, абстрагируем на третьем —
  когда похожее поведение уже проявилось трижды, и общий знаменатель
  виден по фактам, а не по догадке.
- Признак перекоса в DRY: функция с флагами («isExport && !skipValidation
  ?»), интерфейс с единственной реализацией «на будущее», правка одного
  требования в трёх «общих» местах.
- Признак перекоса в KISS: copy-paste в пяти местах, правка константы
  grep'ом по репо.

Ответ одной строкой: KISS — про простоту конкретного решения, DRY — про
единственность знания; конфликт разрешается в сторону простоты, а
обобщение откладывается до третьего повторения.

## 3. Медленный внешний сервис

Симптом: зависимость отвечает 5 секунд, а сервис держит тысячи RPS —
очередь входящих запросов растёт, на каждый повисает горутина (и коннект),
память течёт, деградация одного API валит сервис целиком (каскадный
отказ). Защита строится слоями:

1. **Таймауты везде** — базовый рубеж: у http.Client для зависимости
   свой экземпляр с `Timeout`, у запроса — `NewRequestWithContext` с
   ctx и deadline. Без таймаута «5 секунд» превращаются в «навсегда».
   Бюджет: таймаут зависимости < таймаута собственного входящего
   запроса, чтобы успеть ответить ошибкой, а не молчать.
2. **Ограничение конкурентности (semaphore/bulkhead)**: не более N
   одновременных запросов к каждому зависимому API (`chan struct{}` с
   ёмкостью N, errgroup.SetLimit). Конкурентность на прочие API —
   отдельные пулы (bulkhead): медленный не съедает коннекты здоровых.
3. **Rate limit / backpressure на входе**: когда пул к зависимости полон —
   не копить очередь, а сразу отклонять (429/503, fail fast) или
   деградировать ответом без этого блока. Очередь «на потом» — только
   конечная и осознанная (буфер с отбрасыванием, а не безликая).
4. **Retry с ограничениями**: только на идемпотентные операции и
   ретраебельные ошибки (таймаут, 502/503), экспоненциальный backoff +
   jitter, максимум 1–2 попытки, и никогда — ретраи без лимита
   конкурентности: они множат шторм.
5. **Circuit breaker**: после порога ошибок/таймаутов цепь размыкается —
   запросы к зависимости падают мгновенно (без похода и 5-секундного
   ожидания), периодические пробные проходят в закрытие по успеху.
   Превращает «все горутины висят по 5 c» в «мгновенный fallback».
6. **Наблюдаемость**: метрики p99/ошибок/в полёте per dependency, алерты —
   узнать о деградации раньше пользователей.

Суть ответа: не пытаться «переждать» медленный сервис, а ограничить
влияние его slowness на собственные ресурсы — время ожидания (таймаут),
число горутин/коннектов (лимит+bulkhead), входящую нагрузку (backpressure),
и уметь жить без него (breaker + деградация).
