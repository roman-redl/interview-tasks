# Решение 7 — ревью списания баланса

Главная проблема — гонка «прочитал – проверил – списал» (check-then-act),
разорванная по времени. Уровень READ COMMITTED не защищает: обе транзакции
читают одинаковый `oldBalance`, обе проходят проверку `>= amount`, обе
выполняют UPDATE — баланс уходит в минус. Между ними и внутри транзакции
нет ни одной блокировки конкурирующей строки.

Порядок проблем по убыванию серьёзности:

1. **Гонка списания.** `SELECT balance` → проверка в приложении → безусловный
   `UPDATE ... WHERE user_id` — два параллельных списания одного счёта
   проходят проверку одновременно. Это и есть «потеря денег».
2. **REAL для денег.** Двоичная плавающая точка не представляет 0.1 и
   копит ошибку; деньги — `NUMERIC/DECIMAL` или целые копейки (BIGINT).
   `float32` здесь особенно плох: 24 бита мантиссы.
3. **Ошибки игнорируются.** Ни один `tx.exec` не проверяет возврат: упавший
   UPDATE или таймаут сети тихо вернёт мусор в `newBalance`.
4. **Три круга к строке.** SELECT → UPDATE → SELECT; баланс после списания
   возвращает сам `UPDATE ... RETURNING balance` — и транзакция короче, и
   повторного чтения нет.
5. **Нет идемпотентности.** Retry клиента (например, после сетевого
   таймаута на ответе) спишет сумму повторно — для денег нужен ключ
   операции (operation_id, UNIQUE).

Исправленный вариант (вариант «атомарный UPDATE», обсуждённый на созвоне
как лучший):

```sql
UPDATE users
SET balance = balance - $2
WHERE user_id = $1 AND balance >= $2
RETURNING balance;
```

- строка блокируется на время UPDATE; проверка и списание неразделимы;
- rows affected = 0 → денег не хватает (или счёта нет) — отказ, без
  отрицательного баланса;
- RETURNING даёт новый баланс — лишний SELECT не нужен;
- деньги: NUMERIC; идемпотентность: таблица операций с UNIQUE(operation_id)
  в той же транзакции.

Остальные обсуждённые альтернативы:

- **SELECT ... FOR UPDATE** перед чтением: строка блокируется до конца
  транзакции, второе списание ждёт и перечитывает уже уменьшенный баланс.
  Работает, но держит лок дольше и требует тех же двух шагов — атомарный
  UPDATE проще и короче.
- **SERIALIZABLE**: защищает автоматически, но требует обработки
  serialization failure ретраем и держит нагрузку conflict-детекции —
  для точечного списания это стрельба из пушки.
- **Блокировка в приложении** (мьютекс/однопоточная очередь на счёт):
  не масштабируется на несколько инстансов сервиса, ломается при падении
  держателя блокировки. Внутри одного процесса — только если БД не
  доступна вовсе.
