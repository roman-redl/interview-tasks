## 1. Гарантированная доставка карточки приёма

Приём фиксируется офлайн, связь рвётся, ответы теряются, повторы
неизбежны — доставка строится по схеме «очередь на клиенте + идемпотентный
приём на сервере».

**Клиент — durable outbox:**

1. Карточка приёма сразу пишется в локальное постоянное хранилище
   (SQLite/файл на устройстве) с UUID, сгенерированным на клиенте, и
   статусом «не отправлено». Пишем до попытки отправки: зафиксировал —
   значит сохранено, потерять уже нельзя.
2. Фоновая отправка (не в UI-потоке): достаывает неотправленные из
   очереди, шлёт на бэкенд, помечает отправленным только после
   подтверждения сервера.
3. Ретраи: экспоненциальный backoff с потолком (например, 1 с → 2 → 4 →
   ... → 10 мин) плюс случайный jitter ±20–50%: миллион врачей с
   одинаковым ритмом после восстановления связи — это DDoS-синхронная
   волна; jitter рассеивает её во времени.
4. 429 от сервера — это не ошибка, а «приходи позже»: читать
   `Retry-After` и сдвигать следующую попытку; если заголовка нет —
   множитель backoff. Очередь не чистится, всё дождётся своей попытки.
5. Порядок: карточки одного врача шлуться по одной (или с сохранением
   порядка), чтобы поздние правки не обогнали первые — ключ
   идемпотентности решает дубли, последовательность — очередью FIFO на
   клиента.

**Сервер — идемпотентный приём:**

- UUID карточки — уникальный ключ в БД: повторный POST той же карточки
  не создаёт дубль, возвращает 200/201 повторно (а не 500);
- шейкдаун-волна после восстановления: gateway rate limit с 429 +
  Retry-After, очередь приёма с батчингом INSERT'ов, autoscaling;
- учитывать в SLA: приём карточки — асинхронный процесс, бэкенду не
  обязательно писать в основную БД синхронно (внутренний outbox →
  обработчик), 202 Accepted.

**Ответ на «что произойдёт, когда все разом начнут отправлять»:** без
защиты — волна запросов, деградация и повторный отказ (thundering herd);
лечится тремя уровнями: jitter на клиентах (рассеять), 429 + Retry-After
на шлюзе (справедливая очередь вместо паники), батчинг/очередь на приёме
(переварить пик).

## 2. Сервис сбора данных по URL для ML-команды

Профиль нагрузки: пишет — поток URL + контекст; читает — редко, но
терабайтами. Это S3-подобный access pattern: метаданные — в СУБД, полезные
данные — в объектном хранилище, стрим — события, а не байты.

### Компоненты

- **Crawler**: получает URL + контекст, ходит по страницам, извлекает
  контент. Ограничение конкурентности по доменам, robots/политики,
  таймауты, ретраи; результат — документы.
- **Объектное хранилище (S3/MinIO)**: сырые HTML и извлечённый текст —
  immutable объекты, ключ вида `crawl/<batch_id>/<url_hash>`. Терабайты
  хранить в PostgreSQL нельзя — только объекты.
- **Метаданные (PostgreSQL)**: таблица заданий и объектов: batch_id,
  url, контекст, статус, путь объекта, размер, чексумма, schema версии
  (ML-команда пересоздаёт датасеты). Выборки фильтруются по метаданным —
  индексы под параметры контекста.
- **Стрим (Kafka)**: событие «объект готов» с метаданными (путь в S3,
  чексумма) — компактно; сами терабайты через Kafka не гоняем: брокер и
  consumer сдохнут, это анти-паттерн (лимиты сообщений, долгие балансы
  партиций, повторное потребление пересылает терабайты).

### Как выглядит выдача терабайтной выборки

ML-команда присылает фильтр → сервис вычисляет по метаданным манифест
выборки: список путей S3 (+ чексуммы, схема, параметры) — сам манифест
тоже объект в S3. Дальше два пути:

- **presigned URLs**: сервис ML качает объекты параллельно напрямую из
  S3, минуя наш сервис — терабайты не проходят через приложение;
  чексуммы дают верификацию целостности;
- **gRPC/стрим-канал**: если нужен контролируемый канал — сервис
  стримит, но тогда он становится узким местом и должен масштабироваться
  на драйве чтения из S3; presigned почти всегда лучше.

Идемпотентность и versioning в S3: перезапуск краула не рвёт ссылки
старых выборок; жизненный цикл (lifecycle) — сырые HTML холодеют в
дешёвые тиры, тексты остаются горячими.

### Kafka как транспорт между сборщиком и ML

Да, но для событий, не для данных: topic `crawl.object.ready` с
метаданными; ML-консюмер ведёт собственные датасеты по событиям (инкремент
без фулл-сканов), сами объекты читает из S3. Если ML-команде нужен
именно pull по запросу — Kafka не нужна вовсе, хватает манифеста + S3;
Kafka оправдана, когда выборки строятся непрерывно по мере поступления.
