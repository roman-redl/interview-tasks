# Решение 1 — ProcessBatches: развитие до продакшена

Базовая реализация — `1-process-batches/main.go` (проверена: 120
элементов → 50+50+20). Устные вопросы созвона:

**Параллельная обработка батчей.** Независимые батчи можно обрабатывать
конкурентно, но с ограничением параллелизма:

```go
g, gctx := errgroup.WithContext(ctx)
g.SetLimit(8) // одновременно не более 8 батчей
for start := 0; start < len(items); start += 50 {
	start := start
	g.Go(func() error {
		end := min(start+50, len(items))
		batch := items[start:end]
		if err := s.saver.Save(batch); err != nil {
			return fmt.Errorf("save [%d:%d]: %w", start, end, err)
		}
		return s.notifyer.Notify(batch)
	})
}
return g.Wait()
```

- отмена и первая ошибка: `errgroup.WithContext` отменяет gctx —
  запущенные батчи досыпают через ctx в Save/Notify, новые не стартуют;
  Wait вернёт первую ошибку;
- граница ошибки: если Notify упал, а Save прошёл — батч сохранён, но
  «не отправлен»: прод требует фиксации прогресса (статусы батчей в БД /
  очередь), иначе повтор всего запуска дублирует сохранения — идемпотентность
  Save по ключу батча или лог этапов.

**Что будет, если пустить все батчи через errgroup без SetLimit.**
`g.Go` не блокирует и не ограничивает: на входе в 100 тыс. строк это
2000 горутин разом — если Save/Notify ходят в БД/сеть: пул соединений
исчерпан, latency растёт, upstream получает всплеск, таймауты каскадом;
если в памяти — ок, но следующая зависимость сломается. Отсутствие
лимита = неограниченный параллелизм = переносим пиковую нагрузку на
зависимость со всеми её пределами (bulkhead и backpressure — тема
ровно об этом). `SetLimit` делает g.Go блокирующим при исчерпании —
подача синхронизируется с реальной скоростью потребления.

**Порядок против параллельности.** Если уведомления должны идти в
порядке батчей — параллелить только Save, Notify — последовательно по
мере готовности (worker с упорядоченной сборкой) или один stage.
