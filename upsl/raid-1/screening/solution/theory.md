## 1. Этапы CI/CD для Go-сервиса

Типовой пайплайн от коммита до прода:

1. **Проверки кода**: `gofmt`/`goimports`, `go vet`, `golangci-lint`
   (staticcheck, errcheck, gosec...), `govulncheck` на известные уязвимости
   зависимостей.
2. **Тесты**: `go test -race -count=1 ./...` — unit + интеграционные
   интеграционные можно отдельной стадией с testcontainers);
   coverage-гейт по политике команды.
3. **Сборка**: `go build` с флагами воспроизводимости (`-trimpath`,
   `-buildvcs`), кэш модулей; docker-образ — multi-stage (сборщик →
   distroless/scratch), сборка под целевую платформу через buildx.
4. **Скан образа**: trivy/grype на CVE, проверка подписи (cosign).
5. **Публикация**: push в registry с тегами по SHA коммита (не `latest`),
   SBOM при требованиях.
6. **Деплой**: helm/kustomize в staging → автотесты/smoke на staging →
   promote того же тега в prod (тот же артефакт!). Стратегия выката:
   rolling / canary (сниженный трафик, метрики, авто-rollback) / blue-green.
7. **Постдеплой**: smoke-пробы, health/readiness, слежение за SLO-метриками
   (ошибки, латентность) с алертом и откатом.

Стержень: один артефакт проходит все стадии; прод касается только то,
что прошло все гейты, и по неизменяемому тегу.

## 2. Контекст в Go

`context.Context` — механизм сквозной отмены и передачи запросовых данных:

- **Отмена и дедлайны**: `context.WithCancel`, `WithTimeout`,
  `WithDeadline` — дерево контекстов отменяется каскадом: отменился
  родитель (клиент ушёл, таймаут вышел) — отменены все потомки, а с ними
  все горутины и операции, принявшие этот контекст. Горутина в Go не
  убивается снаружи — контекст это дисциплина кооперативной отмены:
  каждая длинная операция обязана проверять `ctx.Done()`.
- **Значения**: `context.WithValue` — только запросовые данные (trace id,
  авторизация), не бизнес-параметры; типизированный ключ, не string.
- **Сквозной путь**: request → handler → service → repository → драйверы
  (http.NewRequestWithContext, db.QueryContext, т.д.) — бюджет времени
  запроса распространяется до последнего вызова.

Правила гигиены: контекст — первый параметр (`ctx context.Context`);
не хранить в структурах; не передовать `context.Background()` внутрь
работы — Background только в main/тестах/точке входа фоновых задач;
`context.TODO()` — временная заглушка на время рефакторинга.

## 3. Контекст в запросе к базе

Без контекста (`db.Query` вместо `db.QueryContext`) запрос живёт по своим
правилам драйвера: его нельзя отменить извне — ни таймаутом запроса, ни
уходом клиента, ни рестартом деплоя. Последствия:

- **висячие горутины**: обработчик HTTP не вернётся, пока БД думает;
  клиент уже ушёл по своему таймауту, а горутина держит память и ждёт
  ответа БД; под нагрузкой это копится и приводит к OOM/исчерпанию
  воркеров;
- **утечка соединений**: зависший запрос занимает коннект пула
  (database/sql), остальные ждут `db.SetMaxOpenConns` — сервис
  останавливается целиком, хотя «виновата» одна медленная выборка;
- **долгий graceful shutdown**: сервер ждёт обработчики, обработчики — БД.

С контекстом (`QueryContext(ctx, ...)`) отмена распространяется в драйвер:
запрос закрывается, соединение возвращается в пул, горутина завершается.

Подводный камень, который проверяют следом: тот же ctx на транзакции.
`tx, _ := db.BeginTx(ctx, nil)` + отмена ctx после коммита — если ctx
запроса отменяется до `tx.Commit()` (таймаут кончился в момент коммита),
транзакция откатится, а код подумает, что данные сохранены. Поэтому
коммит — на отдельном жизненном цикле, а не на request-scoped ctx;
аналогично `rows.Close` и `rows.Err()` обязаны проверяться: `rows.Err`
после отмены вернёт context.Canceled.

## 4. Линтеры

- **`golangci-lint`** — агрегатор, стандарт индустрии; включает:
  - `staticcheck` — общий статический анализ (стиль, упрощения,
    подозрительные конструкции);
  - `govet` — подозрительные конструкции (printf-несоответствия,
    копирование локов);
  - `errcheck` — непроверенные ошибки — самая частая защита;
  - `gosec` — безопасность (слабый рандом, SQL-конкатенация, Injection);
  - `revive` — стиль/нейминг вместо умершего golint;
  - `unconvert`, `ineffassign`, `dupl`, `goimports` — гигиена.
- **`govulncheck`** — уязвимости реально достижимые из кода (не просто
  listed в go.sum);
- **`go vet -race`/`go test -race`** — не линтер, но обязательный гейт CI
  на гонки;
- Форматирование: `gofmt`/`gofumpt` + `goimports` — порядок импортов;
- Секретный сканер: gitleaks в pre-push/CI.

Организация: `.golangci.yml` в репо, включение в pre-commit (быстрые
линтеры) и обязательный гейт в CI; `//nolint` — только с обоснованием
в комментарии рядом.

## 5. Опыт с SQL

Вопрос про личный опыт — на скрининге отвечают конкретикой своего стека и
приёмов; скелет сильного ответа:

- **СУБД в работе**: назвать основные (для Go-бэкенда чаще всего
  PostgreSQL, MySQL; для специальных задач — ClickHouse под аналитику,
  Redis под кэш) и роль: схема, запросы, оптимизация, миграции.
- **Уровень владения запросами**: JOIN (внутренний/левый, условия связи),
  GROUP BY + HAVING, оконные функции (LAG/LEAD, ROW_NUMBER, SUM OVER) —
  когда агрегации мало; подзапросы против JOIN; CTE для читаемости.
- **Оптимизация**: `EXPLAIN (ANALYZE, BUFFERS)` как обязательный первый
  шаг; понимать план — seq/index scan, nested loop против hash join,
  оценка строк против фактических; индексы под конкретные запросы
  (порядок колонок, частичные, покрывающие); ловить N+1 в коде и
  закрывать батчами/joins.
- **Работа с БД из Go**: database/sql, пул соединений (MaxOpen/MaxIdle/
  ConnMaxLifetime), транзакции с правильной обработкой ошибок и
  отката, QueryContext с отменой.
- **Миграции**: golang-migrate/goose, обратная совместимость схемы при
  rolling-деплое.

Ключ — не перечислить слова, а показать процесс: «медленный запрос →
EXPLAIN → смотрю план → индекс/переписывание → замер до/после».

## 6. Когда индекс не поможет

**Не поможет:**

- **Низкая селективность**: условие покрывает заметную долю таблицы
  (boolean-флаг, статус с двумя значениями, `sex = 'male'` — ~50%);
  читать почти весь индекс + ходить в таблицу дороже seq scan — planner
  правильно выберет полный проход.
- **Маленькая таблица**: несколько страниц читаются seq scan'ом быстрее,
  чем обход дерева индекса; индекс по справочнику из 100 строк бесполезен.
- **Функция над колонкой**: `WHERE lower(email) = ...`,
  `WHERE created_at + interval '1 day' > ...` — индекс по колонке не
  применим (нужен функциональный/выражение-индекс).
- **Ведущий wildcard**: `LIKE '%domain'` — B-tree не ищет суффиксы.
  (trigram/GIN — отдельный ответ.)
- **Нарушен префикс композитного индекса**: индекс (a, b, c) не работает
  под `WHERE b = ...` без a.
- **Статистика врёт**: устаревшая/несвежая статистика, коррелированные
  колонки — planner неправильно оценивает и не берёт существующий индекс.

**Навредит:**

- **Замедление записи**: каждый INSERT/UPDATE/DELETE обязан обновить все
  индексы таблицы — write amplification; под OLTP-нагрузку лишний индекс —
  прямой налог на TPS.
- **Дефрагментация HOT-апдейтов**: в PostgreSQL UPDATE, меняющий
  индексированную колонку, не может сделать HOT (heap-only tuple) —
  создаёт новые версии строк и обслуживание индексов; индекс по часто
  меняемому полю дорог вдвойне.
- **Память и cache pressure**: индексы живут в shared buffers наравне с
  данными — лишний индекс вытесняет полезные страницы.
- **Index bloat**: частые удаления → раздутые индексы → медленнее и
  больше; REINDEX/CONCURRENTLY в обслуживание.
- **Путаница для planner'а**: десятки похожих индексов — риск
  неоптимального выбора и нестабильных планов.

Правило: индекс создаётся под конкретный запрос (и измеряется до/после), а
не «на всякий случай»; неиспользуемые индексы (`pg_stat_user_indexes`
idx_scan = 0) — искать и удалять.
