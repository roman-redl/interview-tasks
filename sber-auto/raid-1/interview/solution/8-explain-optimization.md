# Решение 8 — MySQL: разбор EXPLAIN и оптимизация запроса

## 8.1. Что говорит план

Три строки — два шага внешнего запроса и зависимый подзапрос:

- **`PRIMARY | mc | ref`**: таблица `manager_clients` читается по индексу
  `idx_manager_id_client_id_uindex` с доступом `ref` по константе
  (`manager_id = '152734'`), затрагивается 1 строка; `Using index` —
  индекс покрывающий, в таблицу не ходим. Идеально.
- **`PRIMARY | m | eq_ref`**: для каждой строки `mc` одна строка
  `members` по `idx_user_id` (`ref = bind.mc.client_id`) — join по
  уникальному индексу, максимум одна строка. Тоже идеально.
- **`DEPENDENT SUBQUERY | cdp | index`** — вот источник десяти секунд:
  подзапрос с `IN (...)` переписан оптимизатором как коррелированный —
  выполняется **заново для каждой строки внешнего запроса**, и в каждом
  выполнении — `type = index`, полный проход индекса `idx_client_id`
  по **189 480 строкам** (`ref = NULL`, поиска по значению нет), фильтр
  `Using where` по phase_id отсекает на чтении (`filtered 20.61%`).
  Порядок квадратичный: строки внешнего × скан индекса.

## 8.2. Оптимизация

Два хода: убрать зависимый подзапрос и дать индекс под его фильтр.

1. **Переписать `IN (коррелированный SELECT ... GROUP BY)` в JOIN на
   производную таблицу** — агрегация считается один раз, а не на строку:

```sql
SELECT m.*
FROM members m
         JOIN manager_clients mc ON m.user_id = mc.client_id
         JOIN (SELECT client_id
               FROM client_deal_phases
               WHERE phase_id IN (45, 47)
               GROUP BY client_id
               HAVING count(*) = 2) cdp ON cdp.client_id = m.user_id
WHERE mc.manager_id = '152734';
```

LEFT JOIN здесь тоже заменён на INNER: условие `mc.manager_id = ...` в
WHERE и так превращает внешнее соединение во внутреннее, а честный
INNER даёт оптимизатору свободу порядка.

2. **Индекс под подзапрос — покрывающий `(phase_id, client_id)`**:
   фильтр по phase_id идёт по первой колонке, группировка по client_id —
   по второй: диапазонный доступ вместо полного скана, `Using index for
   group-by` в идеале. Исходный `idx_client_id` под такой фильтр не
   работает вовсе (проверено планом: `ref = NULL`).

Ожидаемый план после фикса: `DERIVED` cdp c `range` по новому индексу и
агрегацией один раз; внешняя часть — как была (она уже была хорошей).
Семантика сохранена: `HAVING count(*) = 2` по фазам 45/47 считает
повторные вхождения одной фазы дважды (клиент с двумя фазами 45
проходит) — если это не задумано, честная формулировка «указаны ОБЕ
фазы»: `HAVING count(DISTINCT phase_id) = 2` (проверено на
PostgreSQL с тестовыми данными: запрос даёт тот же результат, что
исходный, — равнозначность при переписывании обязательна).
