## 1. Сигналы в Linux

Классификация сигналов, важная для сервиса:

- `SIGTERM` (15) — вежливая просьба завершиться: сигнал остановки по
  умолчанию; именно его посылает `kill` без аргументов и Kubernetes при
  удалении пода;
- `SIGINT` (2) — Ctrl+C, смысл тот же для сервиса;
- `SIGKILL` (9) — убить немедленно: перехватить нельзя, код не выполнится
  совсем (K8s присылает его после terminationGracePeriodSeconds);
- `SIGSTOP`/`SIGCONT` — заморозить/продолжить, не перехватываются;
- `SIGHUP` — «терминал отвалился», традиция — перечитать конфиг;
- `SIGQUIT` (3) — для Go-процесса по умолчанию дампит стеки всех горутин и
  умирает — полезно для диагностики зависшего сервиса;
- `SIGUSR1`/`SIGUSR2` — на усмотрение приложения (например, rotate логов).

Плавная остановка в Go — os/signal + context + Shutdown:

```go
func main() {
	ctx, stop := signal.NotifyContext(context.Background(),
		syscall.SIGTERM, syscall.SIGINT)
	defer stop()

	srv := &http.Server{Addr: ":8080"}
	go func() { _ = srv.ListenAndServe() }()

	<-ctx.Done()          // пришёл SIGTERM/SIGINT
	stop()                // signal.NotifyContext restore: второй Ctrl+C убьёт сразу

	shutdownCtx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
	defer cancel()
	_ = srv.Shutdown(shutdownCtx) // не принимать новое, доделать начатое
	_ = db.Close()
}
```

Порядок в проде (K8s): SIGTERM → preStop hook (снять с балансировщика) →
Shutdown: дренаж коннектов, фиксация оффсетов Kafka, закрытие БД — всё в
бюджет terminationGracePeriodSeconds, иначе SIGKILL.

## 2. Профилирование

- **pprof** — стандарт Go: профили CPU (`/debug/pprof/profile`), heap
  (allocs), goroutine, block, mutex; `go tool pprof` — топ, flamegraph
  (`-http=:8080`); в prod — доступ через sidecar-прокси, включать на лету;
- **runtime/trace** (`go tool trace`) — планировщик, GC-паузы, сетевые
  ожидания; отвечает на «почему простаивала горутина», чего pprof не видит;
- **Бенчмарки**: `go test -bench -benchmem`, сравнение `-count=10` +
  `benchstat`; `-race` на CI;
- **Метрики в рантайме**: Prometheus (histogram p99, GC pause, RSS),
  expvar/runtime.MemStats — находить «деградацию», прежде чем искать место;
- **Нагрузка**: k6/wrk/vegeta — репродуцировать профиль под нагрузкой;
- **Слой системы**: `perf` (on-CPU/off-CPU), `strace`/`dtrace` для системных
  вызовов, flamegraph-стеки (brendangregg/FlameGraph).

Рабочий порядок: метрики → подозреваемый путь → pprof CPU/heap →
trace на точки синхронизации → бенчмарк фикса.

## 3. Визуализация архитектуры

- **draw.io / diagrams.net** — бесплатный стандарт de facto: произвольные
  схемы, есть AWS/K8s-стенсилы, хранение в XML/git;
- **Mermaid** — диаграммы как код (flowchart, sequence, ER) прямо в
  Markdown: ревьюятся вместе с текстом, рендерятся в GitLab/GitHub;
- **PlantUML** — диаграммы как код старше и мощнее, особенно sequence;
- **C4-модель** (context/container/component/code) — не инструмент, а
  способ структурировать: разные уровни для разных аудиторий;
  реализуется в Structurizr, IcePanel или том же draw.io;
- **Excalidraw / Miro** — живые обсуждения и наброски архитектуры.

На собеседовании достаточно: C4 как метод + draw.io/Mermaid как носитель.

## 4. Гарантии доставки в Kafka

Три семантики, и в Kafka они собираются из настроек producer + consumer:

- **At-most-once** — сообщение может потеряться, дублей нет. Продюсер
  `acks=0`/не ретраит, или консюмер коммитит оффсет до обработки.
  Для метрик, логов, телеметрии.
- **At-least-once** — не теряем, но повторы возможны. Продюсер с ретраями
  может отправить повтор (сеть отвалилась после записи до ack), консюмер
  коммитит оффсет после обработки. База для платёжек и вообще данных, если
  потребитель идемпотентен.
- **Exactly-once** — ни потерь, ни повторов. Kafka-транзакции
  (`transactional.id`, `initTransactions/sendOffsetsToTransaction/
  commitTransaction`) + идемпотентный продюсер (`enable.idempotence=true`,
  sequence-номера и dedup на брокере); на консьюмере —
  `isolation.level=read_committed`. Читающий в другую систему получит EOS
  только в пределах Kafka: sink (БД, сторонний API) требует своей
  идемпотентности — outbox + ключ операции.

Рычаги надёжности в проде: `acks=all` + `min.insync.replicas=2` (не
терять при падении реплики), ретраи с backoff, `enable.idempotence=true`
как дефолт (с 3.0 включён), коммит оффсетов после обработки, ручной commit
при батчах, DLQ для ядовитых сообщений.

Итоговая формула ответа: семантика выбирается на стороне приложения;
Kafka даёт блоки (idempotent producer, транзакции, replication), из
которых собирается нужная гарантия.

## 5. Уровни изоляции транзакций

Стандарт SQL: READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ →
SERIALIZABLE; каждый следующий закрывает аномалии предыдущего.

| Уровень | Грязное чтение | Неповторяющееся чтение | Фантомы |
|---|---|---|---|
| READ UNCOMMITTED | возможно | возможно | возможны |
| READ COMMITTED | нет | возможно | возможны |
| REPEATABLE READ | нет | нет | возможны* |
| SERIALIZABLE | нет | нет | нет |

\* в PostgreSQL REPEATABLE READ на MVCC фактически не даёт и фантомов
(снапшот на транзакцию), но сериализационные аномалии (write skew) остаются —
их ловит SERIALIZABLE с SSI; в MySQL/InnoDB REPEATABLE READ тоже закрывает
фантомы через gap locks.

Аномалии коротко:

- грязное чтение — чтение незакоммиченных изменений чужой транзакции;
- неповторяющееся чтение — одна и та же строка при повторном чтении даёт
  другое значение (UPDATE между чтениями);
- фантом — повторный запрос по диапазону возвращает другой набор строк
  (INSERT в диапазон);
- write skew — две транзакции читают пересекающиеся данные и пишут
  непересекающиеся, каждая по отдельности валидна, вместе ломают инвариант
  (двое дежурных одновременно ушли).

Дефолты: PostgreSQL — READ COMMITTED, MySQL — REPEATABLE READ. На практике:
READ COMMITTED + атомарные условные UPDATE (`WHERE balance >= $1`) или
`SELECT FOR UPDATE` для критичных точек; SERIALIZABLE — там, где нельзя
рассуждать о локальных локах, с готовностью к retry на serialization
failure. Реализация — MVCC (снапшоты читателей не блокируют писателей),
InnoDB — MVCC + локи диапазонов.

## 6. Проблемы при деплое

Типовые проблемы и что с ними делать:

- **Миграции БД ломают работающую версию** — расхождение схемы и кода при
  rolling update. Профилактика: миграции обратно-совместимы (expand →
  мигрировать данные → contract через пару релизов), никогда не удалять
  колонку в том же релизе, что и код, который её перестал читать.
- **Разные конфиги/версии окружений** («у меня работало»). Один артефакт
  через все окружения, конфигурация снаружи (env/secret store), IaC.
- **Downtime при выкатке** — старые поды умирают раньше готовности новых:
  readiness-пробы, preStop hook + дренирование из балансировщика, rolling
  стратегия, graceful shutdown (SIGTERM → Shutdown).
- **Откат невозможен** — схема БД уехала вперёд, фича-флаги включены.
  Деплой без даунтайма должен откатываться: фича-флаги, обратная
  совместимость, canary-выкат.
- **Секреты в образах/репо** — скан образов (trivy), secret manager, CI
  проверяет на утечку, ротация.
- **Сеть/DNS-кэш после деплоя** — старые IP у клиентов: TTL, health-check
  балансировщика, connection draining.
- **Незаметный деплой битой версии** — CI-гейты: линтеры, тесты, race,
  сканы уязвимостей, smoke после выката, метрики + алерт на ошибку
  релиза, автоматический rollback по SLO.
- **Человеческий фактор** — кнопка «деплой в прод» без ревью: релиз-сертификат,
  approvals, всё что катится в прод — только через пайплайн.

Стержень ответа: деплой — это не «скопировать бинарь», а совместимость
версий во времени (старый код + новая схема, новый код + старые данные) и
возможность вернуться.
