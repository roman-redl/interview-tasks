# Решение 1 — ревью перевода между аккаунтами

Проблемы реализации:

1. **Deadlock на встречных переводах.** Локи берутся в порядке
   «From, потом To». Перевод A→B берёт A, ждёт B; одновременно B→A берёт
   B, ждёт A — классический deadlock (lock ordering). Фикс —
   детерминированный порядок блокировок: всегда сначала аккаунт с
   меньшим ID (сортировать пару по ID перед локами).
2. **Нет проверки баланса.** `From.Balance -= Amount` с `uint` при
   недостатке средств уходит в underflow: баланс станет гигантским
   числом, деньги напечатались из воздуха. Фикс: проверка
   `if From.Balance < Amount { return ErrInsufficient }` внутри локов.
3. **Отсутствие целостности как класса**: перевод атомарен в памяти
   одного процесса (благодаря двум локам), но это не транзакция: сбой
   процесса между списанием и зачислением (и вообще перезапуск) теряет
   деньги; баланс в памяти не переживает рестарт. Для денег — БД и
   транзакция (или journal/ledger), а мьютексы — только для конкурентного
   доступа в рамках процесса.
4. **Мелочи**: `MU *sync.Mutex` — публичное поле, мьютекс в структуре
   публичен наружу (инкапсуляция), проще value `sync.Mutex` внутри
   Account и методы с указателем; nil-мьютекс и nil-Account не
   проверяются (паника); ошибки не возвращаются вовсе (error всегда nil —
   сигнатура врёт); Amount без валидации (0/переполнение при += для
   uint).

Исправленный скелет:

```go
func ExecuteTransfer(t Transfer) error {
	first, second := t.From, t.To
	if first.ID > second.ID {
		first, second = second, first // единый порядок локов => нет deadlock
	}
	first.MU.Lock()
	defer first.MU.Unlock()
	second.MU.Lock()
	defer second.MU.Unlock()

	if t.From.Balance < t.Amount {
		return ErrInsufficientFunds
	}
	t.From.Balance -= t.Amount
	t.To.Balance += t.Amount
	return nil
}
```
