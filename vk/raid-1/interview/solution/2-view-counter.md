# Решение 2 — сервис счётчиков просмотров

Реализация — `2-view-counter/main.go` (проверена: инкременты, чтение,
персист через рестарт, graceful shutdown). Архитектура под 100k+ RPS —
ниже.

## Почему счётчик — не «UPDATE в PostgreSQL»

`UPDATE views SET n = n + 1` под миллионом просмотров — одна блокировка
на строку, у hottest страниц — сериализация всей нагрузки в одну
транзакцию БД. Счётчик просмотров — аддитивная, теряющая порядок,
статистика: под неё ослабляют требования (eventual consistency) и
меняют модель под запись.

## Слои под нагрузку

1. **Приём и накопление — память инстансов.** Шардированные atomic
   счётчики (реализация в файле): инкремент — lock-free, разные
   страницы не конкурируют; HTTP-фронт отвечает 202 мгновенно.
   Стоимость — окно потери при сбое инстанса, закрываемое пунктом 2.
2. **Персист пачками.** Варианты по нарастающей:
   - периодический snapshot (как в реализации): окно потери = интервал
     flush; дёшево, годится для тренировочной постановки;
   - append-only лог событий/WAL → реплей: потерь нет, дороже на запись;
   - прод: пачками (batch) в Redis (`INCRBY` агрегированных дельт раз в
     N мс) или напрямую в ClickHouse — у счётчиков «изменённое с прошлого
     flush» — это мелкие дельты, а не сами события.
3. **Хранение.** Redis — горячие текущие значения (INCR атомарен,
   шардируется кластером); ClickHouse — события/история и любые срезы по
   времени (то, чего нет у Redis); PostgreSQL — только если просмотры
   редко-горячие и нужны в транзакциях с остальными данными.
4. **Масштабирование.** Инстансы stateless-фронт + общий накопитель:
   любой инстанс обрабатывает любой page_id; sticky-маршрутизация не
   нужна, дельты коммутативны. Redis Cluster шардирует page_id слотами;
   экстремально горячий ключ — локальные дельты в памяти инстансов
   сливаются редкими INCRBY (частота записи в Redis падает на порядки).

## Консистентность и точность

- Инкремент просмотров идемпотентен по своей природе неявно: повтор
  HTTP-запроса = лишний просмотр. Требование дедупликации (F5 не
  считается) — уже отдельная задача: уникальный ключ показа
  (user+page+time-bucket) и HyperLogLog для уникальных, обычный счётчик
  для всех.
- strong consistency не нужна: GET видит значение с лагом в секунды —
  это честный SLA продукта; там, где нужен точный срез, читают
  агрегат из ClickHouse, а не горячий Redis.
- «Просмотры не теряются при сбоях» — жёсткая форма: локальный WAL +
  подтверждение записи до ответа 201; мягкая (обычно достаточная):
  окно flush в N мс и признание потери этого окна при падении инстанса.

## Отказоспособность и пики

- Инстансы за балансировщиком, health-check, autoscaling по RPS;
- Redis — кворумные реплики/персист (AOF everysec); ClickHouse —
  репликация;
- пики сглаживает сама модель: фронт отвечает мгновенно, накопитель
  пишет дельтами с постоянной скоростью; перегрузка входа — 429 +
  Retry-After (просмотр можно потерять осознанно — это не платёж).

## API

`POST /view/{page_id}` → 202, `GET /view/{page_id}` → текущее значение;
при фронт-варианте с gRPC — streaming-инкременты ещё дешевле на
запрос. Протокол простого счётчика уместнее всего в HTTP: клиенты —
браузеры/приложения, а не сервисы.
