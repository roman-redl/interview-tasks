# Решение 1 — система уведомлений

Диаграмма с собеседования (drawio):

![Архитектура системы уведомлений](<../Sys design.drawio.svg>)

Сервер-генератор событий кладёт события в очередь; инстансы сервиса уведомлений читают её
и сохраняют уведомления в БД уведомлений. Доставка клиенту — через WebSocket Gateway
(соединения в памяти), при загрузке страницы накопленное достаётся по HTTP API; параллельно
работают каналы почты (почтовый сервис) и смс; внутренние сервисы общаются по gRPC.

## Ответы на уточняющие вопросы

### 1. Что если пользователь оффлайн?

Уведомление не теряется, потому что сначала сохраняется в базе данных. WebSocket — только
быстрый канал доставки, не источник истины. Когда пользователь снова заходит на сайт, клиент
делает HTTP-запрос к API и получает все накопленные уведомления. Система не зависит от
наличия активного соединения.

### 2. Что если отправка уведомления не удалась?

Типы доставки различаются по критичности. Ошибка записи в базу — критическая: делается retry
с backoff, чтобы гарантировать сохранение. Ошибка отправки через WebSocket не критична:
пользователь получит уведомление через API позже. Для email-уведомлений хранится статус
доставки и делаются повторные попытки — это внешний канал, где важна гарантия доставки.

### 3. Что если очередь доставит сообщение дважды?

Очереди дают at-least-once семантику, дубликаты возможны. Обработка делается идемпотентной:
уникальный `notification_id` и constraint в базе данных не позволяют сохранить одно и то же
уведомление дважды — повторное сообщение не создаёт дубликатов, пользователь не увидит два
сообщения.

### 4. Как масштабировать WebSocket Gateway?

На текущем этапе достаточно одного инстанса с соединениями в памяти. При росте нагрузки
gateway масштабируется горизонтально, и возникает проблема маршрутизации: пользователь
подключён к любому из инстансов, сообщение может уйти не туда. Решение — Redis с mapping
`user_id → инстанс`, чтобы отправлять сообщение туда, где открыто соединение.

### 5. Что если WebSocket сервер упал?

Пользователь теряет соединение, но уведомления не теряются — они уже сохранены в базе.
Клиент при следующем открытии страницы или переподключении получает всё через API. Для
отказоустойчивости gateway дублируется несколькими инстансами. Polling возможен как
fallback для редких сценариев, но не как критическая часть архитектуры.

### 6. Как обрабатывать пики нагрузки?

Пики сглаживает очередь: producers только отправляют события, а Notification Service
обрабатывает их со скоростью, которую позволяют ресурсы. При росте нагрузки инстансы сервиса
уведомлений масштабируются горизонтально, чтобы быстрее разбирать очередь — система не
падает при всплесках активности, например во время турниров.

### 7. Как сделать user preferences?

Добавляется отдельная таблица настроек: какие типы уведомлений и через какие каналы
пользователь хочет получать. При обработке события сервис уведомлений проверяет настройки
и решает, отправлять ли через WebSocket, email или пропустить. Поведением можно управлять
гибко, не меняя основную логику.

### 8. Как система будет развиваться при росте нагрузки?

Старт — просто: один WebSocket Gateway, Postgres как основное хранилище, очередь для
асинхронной обработки. При росте: Redis для маршрутизации WebSocket, retry и DLQ для
надёжности, горизонтальное масштабирование сервиса уведомлений и gateway, оптимизации —
агрегация уведомлений (5 пушей в 1: «5 человек сделали ход» вместо отдельных) и batching
для email. Система эволюционирует без полного переписывания.
