## 1. Deckhouse

Deckhouse — опенсорсная платформа управления Kubernetes от Фланта: он
устанавливает и обновляет кластер и его компоненты, закрывая типовую
эксплуатацию — CSI, ingress, мониторинг (Prometheus/Grafana), логирование,
безопасность, отказоустойчивость — в виде управляемых модулей с
проверенными дефолтами. Идея: не собирать платформу из десятка Helm-чартов
руками, а получить обновляемый distribution с консистентными версиями
компонентов и автоматическими канареечными обновлениями control plane.
Известный зарубежный аналог — OpenShift (дистрибутив Kubernetes с готовой
платформой и автоматизацией обновлений); по духу ближе также Rancher.

## 2. Строка в число

Стандартные способы — пакет `strconv`:

```go
n, err := strconv.Atoi("42")              // база 10, int
n, err := strconv.ParseInt("ff", 16, 64)  // своя база и разрядность
u, err := strconv.ParseUint("42", 10, 64)
f, err := strconv.ParseFloat("3.14", 64)
b, err := strconv.ParseBool("true")       // не число, но тот же сценарий
```

`Atoi` — частный случай ParseInt для десятичной системы; всегда возвращают
ошибку — строка может не быть числом. Альтернативы: `fmt.Sscanf("%d", &n)`
(медленнее, для форматированного разбора), `encoding/json` для чисел из
JSON, генерируемый парсер для высоконагруженного горячего пути
(valyala/fastjson и т.п.). Для пользовательского ввода — только strconv и
проверка ошибки.

## 3. Select

`select` — оператор ожидания нескольких операций с каналами
одновременно, аналог `switch` для каналов:

```go
select {
case v := <-ch1: // первый готовый кейс
	use(v)
case ch2 <- x:
	sent()
case <-time.After(time.Second): // таймаут
	timeout()
default: // если ничего не готово — не ждать
	busy()
}
```

Зачем нужен: не блокироваться на одном канале, когда их несколько.

- готовых кейсов несколько — выбирается случайный (это справедливость,
  а не баг: ни один канал не голодает);
- ни один не готов и есть `default` — выполняется default без ожидания;
- без `default` горутина ждёт первый готовый кейс;
- кейс с nil-каналом никогда не готов — им «отключают» ветку;
- приём из закрытого канала всегда готов (нулевое значение).

Типовые паттерны: таймаут операции, отмена по stop-каналу, ограничение
работы цикла (default + отключение через nil), мультиплексирование.

## 4. Файлы, открытые процессом

- `lsof -p <pid>` — классика: пути, типы (REG/SOCK/PIPE), дескрипторы.
- `ls -l /proc/<pid>/fd` — напрямую из procfs, работает без утилит;
  симлинки на файлы, сокеты показывают `socket:[inode]`.
- Детали сокетов: `ss -p` (или `netstat -p`) — кто держит какой сокет;
  `/proc/<pid>/net/tcp`.
- Количество открытых дескрипторов: `ls /proc/<pid>/fd | wc -l` или
  `cat /proc/<pid>/limits | grep files` (soft/hard limit open files).
- Всё дерево от root: `lsof` без аргументов; по конкретному файлу —
  `lsof /path/to/file` (кто держит файл занятым, umount).

## 5. Два приложения на одном порту

Два приложения не могут слушать один и тот же порт на одном адресе —
bind конфликтует (SO_REUSEPORT — исключение ниже). Значит, между ними
ставят посредника на этом порту, а приложения слушают свои внутренние:

- обратный прокси: nginx/HAProxy/traefik на 80/443, раздаёт по Host
  (server_name) или пути — «два сайта на одном 80-м»;
- в Kubernetes: Service/Ingress — ingress-контроллер терминирует порт,
  правила маршрутизируют к разным Deployment;
- для gRPC/HTTP-2 — та же схема с route по authority/path.

Смежный трюк: SO_REUSEPORT — несколько процессов биндят один порт, ядро
балансирует соединения между ними; это способ масштабировать один и тот же
сервер, а не два разных приложения. Другой смежный вариант — приложение
само слушает порт и проксирует часть запросов второму (sidecar/router),
но это вырожденный прокси.

## 6. Kubelet

Kubelet — агент Kubernetes на каждом узле кластера, «руки» control plane на
машине. Control plane говорит «на этом узле должны работать такие-то
поды» (через API и статические манифесты), kubelet приводит реальность к
желаемой:

- следит за назначенными узлу Pod'ами (от scheduler'а) и запускает их
  через container runtime (containerd/CRI-O) по CRI;
- следит за здоровьем контейнеров, перезапускает упавшие по restartPolicy,
  исполняет liveness/readiness/startup пробы;
- монтирует тома (CSI), подставляет ConfigMap/Secret в файлы и переменные,
  применяет ресурсы/лимиты через cgroups;
- рапортует узлу: NodeStatus, heartbeats (lease), метрики — на их основе
  работают eviction и autoscaler.

Без kubelet узел — просто машина с containerd: кластер ею не управляет.
Kubelet — часть стандартного стека узла: kubelet + container runtime + kube-proxy
+ CNI-агент.

## 7. Deployment и StatefulSet

Общее: оба — контроллеры, управляющие Pod'ами через ReplicaSet-подобную
логику, с селекторами, прорами и стратегиями обновления.

Разница — в идентичности подов:

- **Deployment** — поды взаимозаменяемы: имена случайные (hash-суффикс),
  порядок создания/обновления не важен, тома у каждого пода свои
  (обычно пустышка или общая сетевая ФС). Классика — stateless API.
  Обновление — rolling update interchangeable реплик.
- **StatefulSet** — поды имеют устойчивую идентичность: `name-0`,
  `name-1`, ... Порядок строгий: запуск 0 → 1 → 2, остановка в обратном
  порядке (управляется podManagementPolicy). Каждому гарантирован свой
  PersistentVolumeClaim (volumeClaimTemplate), который мигрирует вместе с
  порядковым номером при пересоздании пода на другом узле. Сетевое имя —
  стабильное через headless Service: `pod-0.svc` — peers находят друг друга
  по адресу. Предназначен для stateful: базы данных, брокеры, кластеры с
  репликацией и leader election.

Практическое следствие: StatefulSet медленнее масштабируется и обновляется
(по одному, строго по порядку), а рестарт реплики — это та же реплика с
тем же диском и именем, что и критично для кворумов (etcd, Kafka, ZooKeeper).

## 8. MAC-адрес публичного DNS

Никак — это вопрос-проверка на понимание уровней сети.

MAC-адрес существует только внутри одного канального (L2) сегмента: он
передаётся в Ethernet-фрейме от устройства к устройству и перезаписывается
на каждом маршрутизаторе. До публичного DNS (например, 8.8.8.8) фреймы с
вашим MAC не доходят: у себя вы видите только MAC своего шлюза по
умолчанию (последнего L3-хопа до вас — `arp -n | grep <gateway-ip>` или
`ip neigh`); MAC DNS-сервера известен лишь в его собственном сегменте сети.
Публичный адрес вообще может не иметь единственного MAC: за anycast-IP
8.8.8.8 стоят тысячи машин в разных дата-центрах.

Что реально можно узнать о публичном DNS — L3 и выше: IP (A/AAAA-запись),
TTL, владельца (whois, AS), RTT. MAC — свойство локального сегмента, не
глобального адреса.
