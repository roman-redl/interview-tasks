# Решение 2 — горутина на каждый элемент

Что не так с `for _, item := range items { go process(item) }`:

- **Горутины никто не ждёт**: main/функция может вернуться раньше, чем
  `process` отработает; уйти из функции = горутины работают вхолостую
  (или программа завершится раньше), результат nobody joins.
- **Неограниченный параллелизм**: число одновременно работающих горутин
  ничем не ограничено — ни количеством CPU, ни внешними ресурсами, на
  которые замкнут `process` (соединения, дескрипторы, лимиты API).
- **Ошибки и паники** из `process` никем не наблюдаются и не собираются.
- Если items захватывается по ссылке и цикл Go <1.22 — classический race
  на переменной цикла (с 1.22 семантика изменена).

**Миллион элементов**: миллион горутин. Горутина дешёвая (~2–8 КБ стек),
но миллион — это гигабайты стеков, взрывной рост планировщика и GC,
высокие latency на всё приложение; если process ходит в сеть — миллион
одновременных соединений/запросов убивает и себя, и цель. Программа либо
падает по OOM, либо превращается в своп-кашу.

**Как ограничить число горутин:**

1. **Worker pool** — каноника: N воркеров, читающих из канала задач;
   задачи подаются в канал, ждём через sync.WaitGroup:
   `for i := 0; i < N; i++ { go worker(jobs) }`; масштаб воркеров =
   лимит конкурентности.
2. **Семафор** — канальная идиома `sem := make(chan struct{}, N)`;
   `sem <- struct{}{}` перед запуском, `<-sem` в defer — паттерн
   semaphore; именно так реализован взвешенный семафор в библиотеке
   **`golang.org/x/sync/semaphore`** (ответ на вопрос «как называется
   библиотека»), а для пула + сбора ошибок — `golang.org/x/sync/errgroup`
   (`g.SetLimit(N)`).

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(64) // не более 64 одновременно
for _, item := range items {
	item := item
	g.Go(func() error { return process(ctx, item) })
}
err := g.Wait() // ждём всех, первая ошибка — наружу
```

Дополнительно: если порядок результатов важен — писать по индексу в
заранее выделенный слайс; если items — поток (не влезает в память) —
worker pool особенно уместен: канал задач читается по мере
возможностей, память не растёт с длиной входа.
